# 2026-08-20 — FA-13 web flasher: flash Faraday firmware from the browser

The `/flash` page (the FA-16 stub) is now the real thing: an ESP Web Tools
flasher that writes the ESP32-S3 firmware over WebSerial. The firmware and its
manifest are served versioned from GitHub releases (FA-17), proxied through the
site so the browser can fetch them.

## The CORS catch

The FA-17 notes assumed GitHub release assets serve `Access-Control-Allow-Origin: *`
— they don't. `github.com/.../releases/download/...` 302s to
`release-assets.githubusercontent.com`, whose final response carries no CORS
header, so a browser fetch straight from faraday.to is blocked. (Verified with
`curl -H "Origin: https://faraday.to"`: `api.github.com` and
`raw.githubusercontent.com` do send CORS; the release-assets CDN does not.)

Fix: two same-origin API routes proxy the assets, so the browser never touches
the GitHub CDN directly:

- `GET /api/flash/manifest` — resolves the latest release via
  `api.github.com/releases/latest`, fetches the versioned manifest, and rewrites
  each part's `path` to the firmware proxy. Both upstream fetches are cached 1h
  (`next.revalidate`), keeping us inside GitHub's unauthenticated API rate limit.
- `GET /api/flash/firmware/[version]` — streams the versioned `.bin` (cached 24h
  in the data cache, `Cache-Control: public, max-age=31536000, immutable` on the
  response). The version is validated against a semver-ish pattern before it's
  spliced into the asset URL.

Proxied bytes were verified byte-identical to the release asset (same SHA256).

## ESP Web Tools integration

`components/landing/flash-installer.tsx` (client) lazy-loads ESP Web Tools and
renders `<esp-web-install-button manifest="/api/flash/manifest">`. Two things
worth recording:

- **Deep-import the pre-bundled build.** The package's `main` entry imports
  `@material/web/textfield/internal/shared-styles.js`, which doesn't resolve
  under our bundler (the build failed with `module-not-found`). The fix is to
  import `esp-web-tools/dist/web/install-button.js` — a self-contained bundle
  whose dialog/stub-flasher code loads as sibling chunks. It registers the
  custom element via a top-level `customElements.define`, so it must be loaded
  inside a `useEffect` (dynamic `import()`), never at module scope, or SSR dies
  on `customElements is not defined`.
- **No types ship with the deep import.** `lib/esp-web-tools-global.d.ts`
  declares the side-effect module; `lib/esp-web-tools.d.ts` augments
  `React.JSX.IntrinsicElements` for the custom element.

The button uses the `activate`/`unsupported`/`not-allowed` slots: a styled
"Connect device" button when WebSerial is available, and — when it isn't — a
clear message plus the manual `esptool` fallback (download from the latest
release, `esptool.py --chip esp32s3 write_flash 0x0 …`), rather than a dead
button.

## Disabling the Improv probe (real-device finding)

Flashing a real board surfaced two false errors in the browser's issues panel:

- `Improv initialization failed. Error: Improv Wi-Fi Serial not detected` on first connect, and
- `Error fetching current state: TIMEOUT` after a successful write.

Both come from ESP Web Tools probing for **Improv Wi-Fi Serial** — the optional
handshake that lets a device be configured onto a Wi-Fi network. Faraday has no
radio and no Improv stack, so the probe can only fail. Fixed by setting
`new_install_improv_wait_time: 0` (ESP Web Tools' documented "disable Improv
detection" switch), in two places:

- the manifest proxy (`site/app/api/flash/manifest/route.ts`) injects it, so the
  current `v0.1.0` release is fixed without a re-release, and
- the release workflow's manifest step (`.github/workflows/release.yml`) now
  emits it, so future published manifests carry it too.
